钻井声成像智能分析系统——去伪影模块开发规范（v1.0）
0. 目标与原则
本规范用于指导“去伪影与图像增强模块”的统一开发，确保：

可扩展：后续新增算法不改基础框架；

可移植：算法可在 FastAPI 服务、离线脚本、未来 Agent 调度中复用；

可组合：支持多算法串联（pipeline）与参数可配置；

可追溯：每次处理过程可回放、可审计、可复现；

可工程化：易于被 Cursor/Codex 自动生成、修改和测试代码。

1. 总体架构约束（与现有三层架构对齐）
前端：Vue3 + Element Plus（任务提交、参数设置、进度查询、结果展示下载）

网关/用户模块：WebFlux + MyBatis（鉴权、任务路由、任务元信息管理）

算法服务：FastAPI 微服务（执行去伪影、增强、可视化与结果导出）

1.1 去伪影模块定位
去伪影算法统一部署在 FastAPI 算法服务中；

每个算法实现为可插拔组件，遵循统一输入/输出接口；

Agent 短期只负责“算法选择与参数建议”，不直接改动底层算法代码。

2.1 命名规则
模块目录使用 snake_case

算法唯一 ID 使用：artifact.<name>.v<major>，如：

artifact.stick_pull.v1

artifact.decentralization.v1

输出文件命名必须带任务ID和步骤序号：
job_<job_id>_step_<n>_<algo_id>.<ext>

3. 算法接口规范（必须统一）
每个去伪影算法必须实现统一接口（伪代码）：

class ArtifactRemovalAlgorithm(Protocol):
    algo_id: str
    version: str

    def validate_input(self, input_data: InputFrame, config: dict) -> None: ...
    def run(self, input_data: InputFrame, config: dict, context: RunContext) -> OutputFrame: ...
    def get_default_config(self) -> dict: ...
3.1 输入对象 InputFrame 必须包含
data: np.ndarray（核心计算矩阵，统一主格式）

data_layout: 如 HWC / CHW / HW

dtype: 推荐 float32

value_range: 如 [0,1] 或 [0,255]

spatial_meta: 深度采样率、方位/周向采样率、工具参数（可空）

source_meta: 原始来源（dlis/png/npy）、文件路径、采集时间、井号等

artifact_tags: 已知伪影标签（可空）

3.2 输出对象 OutputFrame 必须包含
result: np.ndarray

quality_metrics: 字典（SNR、对比度提升、边缘保持指标等）

artifact_detected: 本算法识别到的伪影类型及置信度

run_report:

algo_id / algo_version

config_hash

runtime_ms

warnings

preview_assets: 可选（用于前端快速预览的 png/jpg 路径）

4. 输入输出与数据流转规范（你最关心）
4.1 主结论（推荐）
算法内部统一用 numpy ndarray(float32)；

归档与中间存储优先 npz（含矩阵+元数据）；

前端展示/下载用 png（预览）+ zip（全量）；

dlis 作为上游原始格式保留，不作为算法内部主交换格式。

简单说：DLIS负责“原始权威数据”，NumPy负责“计算”，PNG负责“展示”。

4.2 各格式适用边界
DLIS

用途：采集原始数据归档、可追溯、科研复现；

不建议：在各算法模块间直接传递（解析复杂、耦合高）。

NumPy (.npy/.npz)

用途：模块间流转、中间结果缓存、训练/回归测试；

推荐：npz 中同时保存 data + metadata.json 字段。

PNG/TIFF

用途：可视化、前端展示、报告插图；

注意：PNG仅作为展示结果，不作为唯一“真实计算结果”保存。

4.3 统一元数据最小字段（必须）
job_id, well_id, depth_start, depth_end

sampling_rate_depth, sampling_rate_azimuth

input_format, original_file_uri

preprocess_ops（预处理链）

algo_chain（执行过哪些算法）

created_at, created_by, service_version

5. 配置与参数规范
每个算法必须有 default.yaml；

参数分三级：

safe（默认自动跑）

advanced（专家可调）

experimental（需显式开启）

参数校验使用 Pydantic Schema；

每次运行记录 config_hash（保证可复现）；

禁止在代码中硬编码“魔法常量”，必须可配置。

6. Agent 友好性设计（为未来铺路）
6.1 算法能力声明（必须）
每个算法提供 machine-readable 的 capability.json，示例字段：

algo_id

handles_artifact_types: ["stick_pull", "decentralization"]

input_requirements: 分辨率范围、噪声水平、是否需要井深元数据

output_characteristics: 保边缘/平滑倾向

cost_profile: 耗时、显存/CPU占用

Agent 先读 capability 再做路由。

6.2 Agent 决策日志（必须）
Agent 选择算法时，记录：

输入质量评估结果

候选算法及评分

最终选择及原因

参数推荐依据
用于后续论文“可解释决策”章节。

6.3 短期策略建议
先做规则引擎（阈值+特征判断）；

再逐步升级为轻量 ML 策略模型；

保持“策略层”和“算法层”解耦。

7. 质量控制与测试规范
单元测试：每个算法至少覆盖

输入合法性校验

极端值/空值/异常尺寸

输出形状与范围一致性

回归测试：

固定测试集 + 固定参数

指标波动超阈值自动告警

对比基线：

与原图对比（PSNR/SSIM/边缘保持）

与上个稳定版本对比

可复现要求：

固定随机种子

固定依赖版本

记录 git commit hash

8. API 设计规范（FastAPI）
POST /jobs：提交处理任务（支持单算法或pipeline）

GET /jobs/{job_id}：任务状态与进度

GET /jobs/{job_id}/result：结果下载（npz/zip）

GET /algorithms：算法列表与 capability

POST /agent/recommend：根据输入特征返回推荐算法与参数

8.1 任务状态统一枚举
PENDING | RUNNING | SUCCEEDED | FAILED | CANCELED

8.2 错误码建议
A1001 输入格式不支持

A1002 元数据缺失

A2001 算法参数非法

A3001 算法执行失败

A3002 结果序列化失败

9. 日志、审计与论文支撑
每个任务保存 run_report.json

必须可导出：

输入摘要

参数

算法版本

指标变化

耗时

论文/专利用图需可追溯到 job_id + config_hash + commit_hash

10. 开发约束（给 Cursor/Codex 的硬性要求）
新增算法必须：

实现统一接口

提供 config_schema.py

提供 capability.json

提供最少 3 个单元测试

不允许绕过 registry 直接在 API 中硬编码算法调用；

不允许在业务逻辑层直接读写 PNG 作为唯一数据；

任何会影响结果数值的改动，必须更新回归基线说明；

新模块必须更新 算法接入指南.md。

11. 版本规划建议（落地顺序）
v1（现在）：
stick and pull 去伪影、去中心化伪影、基础清晰度增强 + 规则式 Agent 选择

v2：
多算法串联自动搜索（pipeline tuning）、更完整质量评估指标

v3：
裂隙拾取/崩落拾取 Agent 接入（复用同一任务框架与数据契约）

12. 一句话决策建议（便于执行）
数据流：DLIS入库保真，NumPy中间计算，PNG前端展示

架构：统一接口 + 注册中心 + capability 声明

Agent：先规则后模型，先可解释再追求复杂度
